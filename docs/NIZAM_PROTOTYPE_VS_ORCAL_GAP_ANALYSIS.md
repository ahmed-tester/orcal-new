# تحليل الفجوات: نموذج «نظام» التشغيلي (Manus) مقابل نظام Orcal

> **المرجع الخارجي:** `https://nizam-gxp2gm85.manus.space/` — نموذج واجهات (Prototype) لمنطق «النظام الموحد للخدمات والعمليات المالية».
> **المرجع الداخلي:** كود Orcal الحالي (`app/Services`, `app/Models`, `database/migrations`, `app/Filament`).
> **تاريخ التحليل:** 2026-11-09.
> **طريقة العمل:** تم استعراض كل مسارات النموذج (16 مسارًا) واستخراج نصوصها، ثم تدقيق الكود الحالي خدمةً خدمة ونموذجًا ونمطًا، ومقارنة القواعد بندًا بندًا.

---

## 0. ملاحظات منهجية قبل المقارنة

1. **النموذج بياناته فارغة بالكامل** (كل العدادات = 0، لا توجد عمليات أو حركات مالية). لذلك هو **مرجع منطق وواجهات فقط**، وليس مرجع بيانات أو أرقام.
2. النموذج يعرض **6 أدوار** و**13 نوع خدمة** و**12 حالة عملية** و**14 خطوة** في المسار، بينما الكود الحالي يعمل بـ **10 حالات** وأدوار نظامية عامة (Spatie) و**6 خدمات** مُهيّأة في الـ Seeder.
3. جزء كبير من المنطق **نُفِّذ فعلاً** في Orcal خلال 8–9 نوفمبر (العهدة، الباركود، المطابقة، النواقص، سجل التدقيق، الإيداع المجمع، المبالغ المعلقة، لوحة المسار داخل صفحة المعاملة). أي أن الفجوة اليوم **ليست في الأساس**، بل في: **الأدوار والصلاحيات المرحلية، الأرصدة والتوزيع المالي، الشاشات التشغيلية العامة، والربط المالي الكامل**.
4. ملف `docs/plans/UNIFIED_OPERATIONS_STATUS_MAP.md` (8 نوفمبر) أصبح **متجاوزًا** — يسجل بنودًا ❌ وهي منفذة الآن. يجب تحديثه بعد اعتماد هذا الملف.

### 1.3 الحالات الـ12 (مقابل 10 في الكود)

`جديدة` · `قيد التنفيذ` · `عهدة موظف` · `بالخزنة` · **`سداد/إيداع`** · **`متبقي`** · `مبلغ معلق` · `غير مطابق` · `بانتظار اعتماد` · `مصعد للإدارة` · `تسوية لاحقة` · `مكتملة ومطابقة`

> **الفارق:** الكود يملك `OperationWorkflowStatus` بـ 10 حالات (`new, in_progress, employee_custody, at_treasury, awaiting_approval, mismatched, suspense_amount, escalated, retroactive_settlement, completed`) — **ينقصه: `settlement` (سداد/إيداع) و`remaining` (متبقي)**، كما أن `cancelled` موجود كحقل `status` منفصل وليس ضمن دورة العمل.

### 1.4 مسار الـ14 خطوة

اختيار العميل والخدمة → الإنشاء التلقائي → تحديد من يتحمل التكلفة → تحصيل العميل → عهدة الموظف → تسليم الخزنة → تأكيد استلام الخزنة → **التوزيع المالي** → السداد أو الإيداع → المطابقة الثنائية → معالجة الجزء الناقص → الاعتماد أو التصعيد → تحديث الأرصدة والمؤشرات → الإغلاق.

### 1.5 الأرصدة الخمسة المطلوبة

| الرصيد | المكوّنات |
| :--- | :--- |
| العميل | المستحق، المدفوع، المتبقي، الرصيد الزائد، الديون المتأخرة |
| الموظف | العهدة الحالية، المسلّم للخزنة، المدفوع من ماله، المستحق له |
| الخزنة | المتوفر، المخصص للسداد، المخصص للإيداع، الزائد المرتبط بالعملية، المعلق |
| المكتب | التزامات المكتب، المسدد، المتبقي |
| المؤشر المالي | المتوقع، المدفوع الموثق، المتبقي، المعلق، غير المعتمد، المتأخر والفروقات |

### 1.6 محاور المطابقة الخمسة

الخدمة (نوعها ورقم العملية) · المبلغ (المتوقع مقابل المسدد) · الجهة (الطرف المقابل الموثق) · **الفاتورة/السند** (رقم الفاتورة ومرجع السند) · المستند (الإثبات المرفق والمعتمد).

### 1.7 الاستثناءات الثمانية

خدمة منفذة مسبقًا · دين على العميل · على المكتب · تكلفة مشتركة · سداد شخصي للموظف · فرق مالي · مستند ناقص · إلغاء (بسبب + اعتماد المشرف + عدم إسقاط العهدة أو حذف التاريخ).

| 9 | المبلغ المجهول: حجز → اقتراح ربط → اعتماد | 🟡 | `UnifiedSuspenseAmount` + `suggestMatchingTransactions` (مطابقة مبلغ فقط) + `allocateSuspenseAmount` — **بدون شاشة، بدون اعتماد، وبدون تسجيل تدقيق عند التخصيص** |
| 10 | مطابقة ثنائية (5 محاور) + محرك نواقص + قاعدة المسؤولية | 🟡 | `OperationsReconciliationService::evaluate()` 4 محاور (طرف مقابل/عهدة/إثباتات/فروقات) — **لا محور فاتورة/سند، ولا مقارنة مع حركة مالية، والنقص يُسند لـ `executed_by` دائمًا** |

## 6. فروق منطقية دقيقة تستحق الانتباه (قراءة الكود)

1. **العهدة تسبق القبض:** في `ServiceTransaction::saving()` تُضبط `custody_status = on_employee` بمجرد أن `paid_amount > 0`، والمعالج يضع `paid_amount = price` تلقائيًا عند اختيار خدمة بتحمّل `client_paid`. أي أن **إنشاء العملية وحده يجعل المال «عهدة على الموظف»** قبل أي قبض فعلي. المطلوب: فصل «المبلغ المتوقع» عن «المبلغ المحصل».
2. **المطابقة تُحسب مرتين:** `saving()` تعتمد شرطًا مبسطًا (`payment_proof` + عهدة محلولة)، بينما `evaluate()` تطلب `gov_payment_receipt` و`bank_deposit_receipt` وطرفًا مقابل. النتيجة: تعارض محتمل بين الشارة في الجدول وحاجز الإغلاق.
3. **الفاتورة تُنشأ بلا رابط:** `ServiceTransactionObserver` يخزّن `metadata.auto_invoice_id` فقط، ودون `customer_id` — فلا يمكن للمطابقة أن تقارن «رقم الفاتورة/السند» كما يطلب النموذج.
4. **مهمة النقص تُسند دائمًا للمنفذ:** `syncDeficiencyTasks` تستخدم `executed_by ?? employee_id`، بينما النموذج يوزّع: نقص الطرف المقابل/المستند → الموظف، نقص المبلغ → مسؤول السداد، نقص الاعتماد → المشرف.
5. **الإيداع المجمع لا يمسّ الخزينة:** `createBatchDeposit` يحدّث `metadata` فقط (`batch_deposit_id/number`) — بلا `TreasuryTransaction` ولا انخفاض في الرصيد.
6. **تخصيص المبلغ المعلّق بلا تدقيق:** `allocateSuspenseAmount` يعدّل `paid_amount` دون `OperationsAuditService::record` (بقية العمليات مسجلة).
7. **`resolveEscalation` لا يمسح `escalated_at`** — قد يعود `resolveWorkflowStatus()` إلى `ESCALATED` بعد فك التصعيد.
8. **لا نطاق لكل موظف:** كل الاستعلامات مقيدة بالشركة (`company_id`)، بينما لوحة الموظف في النموذج تعرض **عملاءه ومهامه فقط**.

## 8. خطة تنفيذ مقترحة

### المرحلة 1 — تصحيح المنطق المالي (قبل أي واجهة)
1. جدول وخدمة **التحصيلات** (`Collections`) + زر «تسجيل تحصيل» (كلي/جزئي) + تأكيد التسليم.
2. إزالة اشتقاق `reconciliation_status` من `saving()` وحصر المطابقة في الخدمة.
3. ربط الفاتورة بالعملية (`invoices.service_transaction_id`) + رقم إيصال.
4. أرصدة مشتقة (`BalanceService`): عميل/موظف/خزنة/مكتب + المؤشر المالي.
5. اختبارات Feature: التحصيل → العهدة → الاستلام → عدم الإغلاق قبل المطابقة.

### المرحلة 2 — الخزنة والتوزيع والسداد
1. `TreasuryDistributionService` + جدول توزيعات (سداد/إيداع/زائد).
2. شاشة السداد والإيداع (3 تبويبات) + اعتماد + سند إيداع مطبوع.
3. تحويل دفعة الإيداع والسداد إلى حركات مالية فعلية.
4. اعتماد وتدقيق المبالغ المعلقة.

### المرحلة 3 — المطابقة والنواقص والحوكمة
1. شاشة المطابقة والنواقص + محور الفاتورة/السند.
2. توجيه مهام النقص حسب نوع النقص.
3. شاشة بنك المهام + إشعارات مرحلية + SLA/تصعيد مجدول.
4. مسار إلغاء باعتماد + 6 أدوار تشغيلية + مصفوفة صلاحيات.

### المرحلة 4 — اللوحات والتقارير
1. لوحة المتابعة (المؤشرات الست + الحالات + صحة المسار).
2. لوحتي كموظف + لوحة الإدارة.
3. تقارير الأداء (موظف/خدمة/قسم/عميل).
4. دليل المخطط داخل النظام + تحديث `SYSTEM_CHEATSHEET.md`.

## 10. الخلاصة في سطر واحد

> Orcal تملك اليوم **المحرك** (إنشاء تلقائي + عهدة + استلام خزنة + سداد/إيداع مجمع + مطابقة + نواقص + تدقيق)، والنموذج يضيف **الطبقة التي تجعل المحرك مقروءًا ومحكومًا**: تحصيل موثق، توزيع مالي، أرصدة، أدوار مرحلية، شاشات تشغيل، لوحات ومؤشرات. الأولوية القصوى ليست نسخ الواجهات، بل **إغلاق الفجوات P0 المالية** أولًا.
