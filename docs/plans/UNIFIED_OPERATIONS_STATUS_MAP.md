## 1. منطق الملف — ملخص ما يجب أن يعمل (المبدأ السيادي)

1. الخدمة تُنشأ مرة واحدة وماليتها تلقائيًا (فاتورة/استحقاق + رقم عملية + مسؤول + مبلغ متوقع).
2. المال يسير في دورة موثقة واحدة: **عميل → عهدة موظف → خزنة → سداد/إيداع → مطابقة → إغلاق**.
3. العهدة تنتقل بوسيلة تحقق فورية (باركود + رقم العملية) ولا تُسقط إلا بتأكيد الخزنة الفعلي.
4. التوزيع داخل الخزنة: مخصص سداد + مخصص إيداع + زائد يبقى مرتبطًا بالعملية.
5. الإيداع المجمع = دفعة بنكية واحدة تخدم عدة عمليات مع حفظ تفصيل كل جزء.
6. المبلغ المجهول يحجَز كمعلق، ولا يُرحّل إلا بعد اعتماد التصحيح.
7. المطابقة الثنائية: خدمة ↔ حركة مالية (المبلغ، الجهة، الفاتورة/السند، المستند) — والنقص يعزل في مهمة لمسؤول الجزء الناقص فقط دون تعطيل باقي الفريق.
8. حالات العملية: جديدة / قيد التنفيذ / عهدة موظف / بالخزنة (متبقي سداد-إيداع) / مبلغ معلق / بانتظار اعتماد / غير مطابق / مصعد للإدارة / تسوية لاحقة / مكتملة.
9. بنك مهام + تنبيهات مرحلية + تصعيد خارج الصلاحيات.
10. أرصدة (عميل/موظف/خزنة/مكتب) ومؤشر مالي وتقييم أداء، وسجل تدقيق إلحاقي لا يُحذف.
11. استثناء وحيد: الصناديق المستقلة (أصول/قروض/جمعيات) تبقى خارج المسار.

## 3. الترتيب المقترح للتنفيذ (مراحل صغيرة، كل مرحلة قابلة للتسليم)

- **المرحلة A — متابعة مالية صحيحة (بأساس قائم):**
  1. `ServiceTransactionObserver` جديد: إنشاء الفاتورة/الاستحقاق + الدين تلقائيًا (تعمل بدون تغيير شاشات).
  2. تقسيم الإثباتات: تحويل حقل الرفع إلى سندَين (سداد حكومي + إيداع بنكي) وفق البيانات المستخدمة بالفعل في النموذج.
  3. حالات العملية الموحّدة (`workflow_status`) على الحالات 9 بالملف + تصويب حقل الحالة بالشاشة.
- **المرحلة B — سداد/إيداع/علوّق:**
  4. `OperationsSettlementService`: سداد للجهة + إيداع فردية، وإيداع مجمّع مع الاحتفاظ بالتفصيل لكل عملية.
  5. جدول وخدمة «المبالغ المعلقة» (حجز → اقتراح ربط → اعتماد → ارتساب).
- **المرحلة C — المطابقة الثنائية + النواقص:**
  6. `OperationsReconciliationService` (مطابقة خدمة↔حركة + دفعة/جهة/سند/مستند) مع سجل مُعاد المطابقة.
  7. محرك النواقص → إنشاء مهام بنك المهام لصاحب الدور الناقص (استخدام وحدة `Tasks` القائمة بالربط وليس بناء وحدة جديدة).
- **المرحلة D — الاعتماد + الأحكام:**
  8. تدفق اعتماد/تصعيد (مشفَر على `HasApprovalStatus` المحلي).
  9. إغلاق محكم: قيد الإغلاق بجابها (سنن المتوثقة).
- **المرحلة E — التدقيق والمؤشرات:**
  10. سجل تدقيق إلحاقي (جدول `audit_logs` + منع حذف/تعديل عبر Policy أو query لا update/deleting).
  11. أرصدة موحدة + الأداء: widgets لوحة تغطية رؤوس البيانات.

> قاعدة التنفيذ نفسية داخلية: كل مرحلة إكمال = service + migrations جديدة + اختبار Feature قصير + `php -l` + `pint`، وبدون تعديل migrations منفذة.

## 4. البنود المطلوب توضيحها (خط الأفكار الأرجح قبل بدء كل مرحلة)

1. الحالة الوحيدة الفعالة لأوراق العمل (2.1) بتوصيف `A0.1.A6.4.A2` هل انت أساس: **هل نُتابع على أساس `service_transactions` نفسه؟** (الموصى به).

2. الفاتورة الدائمة: هل الفاتورة `Invoices` الموجودة مرتبطة بسير العمل ولا شاشته الخاصة، أم بقى **فاتورة أُوتوماتكية فقط عند الإنشاء؟**
3. الباركود: هل نطلق `BarcodeService::generateSvg` (SVG القائم بدون اعتماديات جديدة) كوسيلة التسليم الرسمية؟
4. للمودول: `financial_operations()` join `service_transactions` (الخط النهائي)؟
